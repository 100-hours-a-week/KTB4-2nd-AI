# 정리부터 검색과 스토리까지 연결 확인

이 검증은 테스트용 BE 입력을 Kafka로 전달하고 AI의 HTTP 응답과 Kafka 결과를 확인합니다. 실제 BE의 권한 필터, DB 저장과 화면 표시까지 검증하는 도구는 아닙니다. `photos_ready`의 보관과 취소 및 장애 복구는 별도의 통합 테스트에서 확인합니다.

## 로컬 통합 테스트

Redis와 Kafka를 실행한 뒤 저장소 루트에서 실행합니다. 테스트는 별도 이름의 토픽과 Redis prefix를 만들고 종료할 때 자신이 만든 자료만 제거합니다. 운영 브로커에 테스트 주소를 지정하지 않습니다.

```sh
JOBS_TEST_REDIS_URL=redis://127.0.0.1:6379/0 \
JOBS_TEST_KAFKA_URL=localhost:9092 \
uv run pytest tests/test_ai_e2e.py tests/test_v2_jobs_integration.py -q
```

FastAPI 두 프로세스와 정리 실행기를 실제 진입점으로 띄웁니다. 모델과 S3 및 Qdrant 서버는 로컬 HTTP 대역이며, 애플리케이션은 실제 SDK와 정리 및 검색과 스토리 함수를 사용합니다. JPEG 다운로드와 원본 바이트 임베딩, 벡터 저장과 검색, URL 서명과 사진 읽기, 스토리 생성, 두 API의 상태 조회와 Kafka 결과 및 지표를 검증합니다. 이 결과를 실제 GPU 추론이나 사진 품질 측정으로 해석하지 않습니다.

## 실제 서버 연결 검증

먼저 API 두 개와 정리 실행기, Redis, Kafka, Qdrant 및 두 모델 서버를 기동합니다. `docker/v2/.env.example`에 안내한 설정과 인증을 준비하고 `SEARCH_ENABLED=true`, `JOBS_FAKE_PIPELINE=false`, 실제 정리 및 스토리 핸들러를 사용합니다. 생성 모델이 여러 장의 이미지와 구조화 출력을 지원하는지 확인합니다.

`e2e-case.example.json`을 별도 파일로 복사한 뒤 BE가 제공한 테스트 여행과 사진 ID, S3 사본 경로, 원본 촬영 시각 및 EXIF 좌표로 바꿉니다. 예시는 입력 형식만 보여 주며, 예시에 적힌 ID로 공유 환경을 호출하지 않습니다. 날짜와 장소가 확인되고 정리 후 ACTIVE가 될 사진을 선택합니다. 스토리 입력에는 BE가 저장한 장소 ID와 보정된 시각을 사용합니다. 검색 후보는 동일한 테스트 사용자가 소유한 ACTIVE 사진으로 구성합니다.

검증 도구는 전용 소비자 그룹으로 결과를 읽으며 BE의 소비 offset을 변경하지 않습니다. 요청마다 새 execution_id를 생성합니다. 요청과 벡터 및 작업 기록은 서버에 남으므로 테스트 데이터의 정리 책임은 BE 및 운영 담당과 맞춥니다. 시작할 때 전체 토픽 목록으로 업무 토픽 6개가 이미 존재하는지 확인하고, 하나라도 없으면 요청 전에 실패합니다. 배포 브로커에서도 자동 토픽 생성을 비활성화합니다. 토픽 생성 명령이나 기존 데이터 삭제 명령은 실행하지 않습니다.

저장소 루트에서 필요한 환경변수를 주입하고 실행합니다. 설정 파일은 Git에 추가하지 않습니다.

```sh
uv run python -m scripts.check_v2_e2e /path/to/test-case.json \
  --api-url http://api-a:8000 \
  --api-url http://api-b:8000 \
  --output /path/to/e2e-result.json
```

두 API 주소를 지정하면 각각 상태와 지표를 확인합니다. ALB 주소 하나만 지정하면 두 복제본을 개별 확인했다고 판단하지 않습니다. `process` 결과 이후 질의 해석과 검색 및 답변을 확인하고, 마지막에 `story` 결과를 받습니다. 요청 timeout에 60초를 더한 기간 안에 결과가 없으면 실패하므로 작업 대기열이 비어 있는 테스트 환경에서 실행합니다. 보고서는 기능별 경과 시간과 수신 상태, 작업의 실행 ID를 담으며 사진 내용이나 URL을 저장하지 않습니다. 실패 시에도 마지막 단계와 실행 ID 및 오류 종류를 보고서에 저장하고 종료 코드로 알립니다. 자세한 원인은 해당 실행 ID로 서버 로그에서 확인합니다. Kafka 클라이언트 종료는 각각 10초까지만 기다립니다.

이 도구의 경과 시간은 클라이언트가 요청을 발행한 후 결과를 받은 시간입니다. `/metrics`의 작업 시간은 Redis 접수에서 AI 결과 저장까지이며 Kafka 전달 시간과 구분합니다. 실제 서버 검증을 통과한 다음 BE에서 결과를 저장하고 FE에서 표시하는 흐름을 별도로 확인합니다.
